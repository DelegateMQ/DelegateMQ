15// Async delegate message priority
16//
17// Contract every dmq::os::Thread port's queue implementation must uphold:
18// a HIGH message is always dispatched ahead of any NORMAL message already
19// waiting, but HIGH does NOT mean "jump to the very front" -- among multiple
20// HIGH messages (or multiple NORMAL messages), FIFO order relative to each
21// other must be preserved. I.e. per-priority-lane FIFO, not a LIFO stack.
22//
23// A single queue with a "send to front" primitive (FreeRTOS xQueueSendToFront,
24// ThreadX tx_queue_front_send) gets this wrong: a second HIGH message sent to
25// the front lands ahead of the first HIGH message, turning HIGH ordering into
26// a stack. The correct shape -- used by every port -- is two lanes (one per
27// priority) with new messages always pushed to the BACK of their lane, and
28// the consumer draining the HIGH lane before the NORMAL lane:
29// - StdlibThread / Win32Thread: two std::deque, one shared mutex+condition_variable.
30// - ZephyrDelegateQueue: two k_msgq, drained via k_poll on both.
31// - CmsisRtos2: native osMessageQueuePut msg_prio gives this directly (no dual lane needed).
32// - FreeRTOSDelegateQueue / ThreadXDelegateQueue: two native queues, woken by
33// one shared counting semaphore "doorbell" (the RTOS-native stand-in for
34// the stdlib condition_variable, since neither queue API exposes one).
35enum class Priority
36{
37 NORMAL,
38 HIGH
39};
